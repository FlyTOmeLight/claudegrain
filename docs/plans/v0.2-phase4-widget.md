# v0.2 Phase 4 — Desktop Widget

WidgetKit-based macOS desktop widget surfacing Claudegrain Session Block + spend at small/medium/large sizes.

---

## 1. ADR draft — packaging approach

**Decision: Option (d) — restructure as Xcode workspace, keep ClaudegrainCore as a SwiftPM package dependency.**

`Package.swift` stays the source of truth for `ClaudegrainCore`. A new `Claudegrain.xcodeproj` (committed) hosts the app target (`ClaudegrainApp`) and the widget extension target (`ClaudegrainWidget`), both depending on `ClaudegrainCore` via local SwiftPM reference. Reasoning:

- (a) `swift package generate-xcodeproj` is removed in Swift 5.7+. Dead.
- (b) Hand-written Xcode project alongside SwiftPM duplicates target definitions; drift inevitable.
- (c) SwiftPM custom build phases producing a `.appex` is unsupported by Apple — codesigning, embedding, entitlements, App Group provisioning all break.
- (d) Costs one-time restructure; gains first-class extension support, embedded provisioning, future-proof for Notification Service Extension / Login Item helper / Sparkle.

Migration: `ClaudegrainCore` source files stay where they are. `ClaudegrainApp/` source files stay where they are. `Sources/ClaudegrainSpike` and `Sources/ClaudegrainPreview` stay as SwiftPM-only executables. The new Xcode project references `Sources/ClaudegrainApp/` and a new `Sources/ClaudegrainWidget/` directly. `swift build` continues to work for the library and the spike/preview executables; the menu bar app builds via `xcodebuild` from the Xcode project. `scripts/build-dmg.sh` switches from `swift build -c release --product claudegrain` to `xcodebuild -project ... -scheme Claudegrain -configuration Release archive`.

Why this is the least-bad option: matches how every shipping macOS app with extensions is structured. The other three either don't work, drift, or rely on undocumented SwiftPM hacks.

## 2. Architecture sketch

New targets:

- `ClaudegrainWidget` (app extension, `.appex`, bundle id `dev.claudegrain.menubar.widget`) — WidgetKit + SwiftUI views + `TimelineProvider`. Reads only.
- `ClaudegrainSharedUI` (new SwiftPM target inside `Package.swift`, depended on by both `ClaudegrainApp` and `ClaudegrainWidget`) — Theme, FontRegistry, sparkline view, formatters. Pure SwiftUI, no AppKit.

Data flow:

```
ClaudegrainApp (host)
  AppCoordinator.refreshDerivedNow()
    └─ EventsDatabase queries (existing)
    └─ WidgetSnapshotWriter.write(snapshot)         ← new
         └─ App Group container:
              group.dev.claudegrain.shared/
                widget-snapshot.json                ← atomic write
         └─ WidgetCenter.shared.reloadAllTimelines() ← throttled, see §4

ClaudegrainWidget (extension)
  WidgetSnapshotProvider.timeline(in:)
    └─ App Group container read
    └─ Decode WidgetSnapshot
    └─ Build TimelineEntry array
```

App Group container: `group.dev.claudegrain.shared`. Lives at `~/Library/Group Containers/group.dev.claudegrain.shared/`. The widget cannot access `~/Library/Application Support/claudegrain/cache.db` — sandboxed extensions only see their own container plus group containers.

Cache.db migration: **do not move**. The widget never reads SQLite. It reads only a flat JSON snapshot file the host writes. Keeps SQLite path stable, avoids GRDB inside the extension, keeps the extension binary tiny (memory budget for widgets is ~30MB).

`commitments.json` stays where it is (host-only).

## 3. Data shape

Defined once in `ClaudegrainCore`, no UI dependency:

```swift
public struct WidgetSnapshot: Codable, Equatable, Sendable {
    public let schemaVersion: Int               // start at 1
    public let generatedAt: Date
    public let language: String                 // "en" | "zh"
    public let primaryMetric: String            // "spend" | "tokens"
    public let dataSourceStatus: String         // "oauthLive" | "jsonlOnly" | "cliFallback" | "offline" | "unknown"

    // Hero
    public let sessionBlockPercent: Double?     // 0..1; nil ⇒ unknown
    public let sessionBlockResetAt: Date?
    public let weeklyPercent: Double?           // 0..1
    public let todayCostUSD: Double
    public let todayTokens: Int

    // Medium adds
    public let weekSpend: [Double]              // 7 entries, oldest → newest

    // Large adds
    public let topRepos: [Repo]                 // up to 3
    public let cacheHitRate: Double             // 0..1

    public struct Repo: Codable, Equatable, Sendable {
        public let name: String                 // shortened cwd
        public let costUSD: Double
        public let percentOfDay: Double         // 0..1
    }
}
```

Contract:

- Single file `widget-snapshot.json` in App Group container. Atomic write (`.atomic`). Versioned via `schemaVersion: Int` — extension drops snapshots with unknown version and shows placeholder.
- Snapshot bytes target: <8KB. Top-3 repos cap, no per-tool list, no model mix in widget.
- Timestamps as ISO-8601 with fractional seconds (default Codable behavior fine).

`WidgetSnapshotWriter` (in `ClaudegrainCore`) takes the existing `AppModel` published values + `EventsDatabase` queries, builds the struct, writes atomically. `WidgetSnapshotReader` (also in Core, used by extension) decodes and returns Optional. Both targets link Core; no duplication.

## 4. Timeline strategy

Rules:

- **Reload trigger from host**: `WidgetCenter.shared.reloadAllTimelines()` is called from `AppCoordinator.refreshDerivedNow()` after writing the snapshot, but **throttled to once per 5 minutes** via a debouncer. WidgetKit budgets ~40 reloads/day system-wide; bursting on every JSONL ingest would burn the budget and OS would silently drop reloads.
- **Timeline policy**: provider returns a single entry with `.after(Date().addingTimeInterval(15 * 60))`. The system then re-asks for a timeline ≤30 min later; we re-read the (possibly newer) snapshot file. Effective freshness = min(host throttle, 15 min).
- **Placeholder + snapshot**: `placeholder(in:)` returns a frozen sample with realistic numbers ("$3.42", 47% session, sample sparkline). `snapshot(in:)` for gallery uses the same sample. Both ignore disk to render fast.
- **First-launch race**: if no snapshot file exists yet, the provider returns an entry with `WidgetSnapshot.empty` and a "Open Claudegrain to populate" UI string. Timeline policy stays the same — first host write fixes it.
- **App quit**: when the host app is not running, the widget keeps showing the last snapshot stamped with `generatedAt`. The footer of medium/large shows relative time ("2h ago") and dims to `inkFaint` if `> 30min` old. Small size shows a single dot indicator if stale.

No interactive widgets, no AppIntents, no deep-link refresh button — Phase 5 territory.

## 7. Risks (top 3)

**R1 — Codesigning + provisioning churn.** Two bundle ids now (host + extension), both need the same Team ID, both need the App Group entitlement, the extension must be embedded with `--deep` *and* have its own explicit entitlements file in Hardened Runtime. Failure mode: notarization rejects, or the widget fails to read the App Group at runtime with `Operation not permitted`.
*Mitigation*: T05 includes a smoke-test script `scripts/verify-widget-entitlements.sh` that runs `codesign -d --entitlements - <appex>` and greps for `group.dev.claudegrain.shared`. CI runs it on every PR. Document the exact `DEVELOPER_ID` + `TEAM_ID` env vars in `docs/RELEASE.md`.

**R2 — App Group container migration.** Existing users have data at `~/Library/Application Support/claudegrain/cache.db`. They do **not** have `~/Library/Group Containers/group.dev.claudegrain.shared/`. First launch after upgrade writes the snapshot file there; the directory is auto-created on first access. Risk is sandbox confusion — if we ever later sandbox the host app, `cache.db` would need to migrate to the container too.
*Mitigation*: explicit decision in ADR-0012: cache.db stays in Application Support, widget snapshot lives in App Group container. They are separate concerns. No data migration needed for v0.2. If/when the host gets sandboxed (Phase 6+), do migration then.

**R3 — Bundled fonts inside extension.** The host registers JetBrains Mono via `CTFontManagerRegisterFontsForURL(.process)` which only registers in the host process. The widget extension is a separate process and won't see those fonts.
*Mitigation*: ship the same `.ttf` files inside the widget extension's resources and register at extension launch. Same `FontRegistry.registerAll()` runs in `WidgetSnapshotProvider.init()`. Bundle size cost ~600KB per extension — acceptable. Verified in T07 snapshot tests (rendered output must show JetBrains Mono glyphs, not San Francisco fallback).

## 8. Out of scope

- Interactive widgets (App Intents / button taps). macOS 14 supports them; defer to Phase 5.
- Lock Screen / StandBy widgets — iOS-only.
- iOS / iPadOS support entirely.
- Custom widget configuration (size override, theme override, repo filter). All v0.2 widgets are zero-config.
- Sandboxing the host app. Out of scope for the same reason cache.db isn't migrating.
- Push-style refresh from background daemon. The host app must be running for snapshots to update; that's documented behavior.
- Sparkle / auto-update wiring through the extension. Extension follows the host app version.
- Widget for the Notification Center / Today view — the macOS desktop widget already covers it.
