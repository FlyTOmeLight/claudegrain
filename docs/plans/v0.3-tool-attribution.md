# v0.3 — Tool-level attribution (theme C)

Status: planning
Replaces: ADR-0003's primaryTool simplification (kept as
`--legacy-attribution` audit mode).
Touches: ADR-0001, ADR-0002, ADR-0003.

## Goal

Stop attributing 100% of a turn's tokens to its first `tool_use`
block. Split tokens proportionally across all `tool_use` blocks in
the turn, document the algorithm, expose per-tool numbers in the
popover.

## Why

ADR-0003's "first tool wins" simplification was load-bearing for
v0.1 — it let us ship per-tool labels without a complex split.
The cost: a single Bash call early in a turn that did nothing
gets credited for the entire turn's tokens, including the 50k
output tokens that came from a Read on the next call. Power users
who watch the popover have flagged this since v0.1 launch.

v0.3 replaces it with a documented split. ADR-0015 picks the
algorithm; this plan executes it.

## Algorithm decision (ADR-0015 draft)

Two candidates:

**(α) Block-count proportional**: turn has N `tool_use` blocks ⇒
each block gets `tokens / N` of the turn's output tokens. Simple,
deterministic, treats every tool as equal.

**(β) Byte-weighted**: each block weighted by
`len(tool_input) + len(tool_output)`. Heavier tools get more
share. Closer to "actual cost" intuition but unstable when
`tool_output` is structured JSON vs. raw text — bytes ≠ tokens.

**Decision: (α) block-count proportional**. Reasons:
- Stable across renderings (vs. byte-weight which depends on
  whitespace and JSON shape).
- No need to count tokens from tool outputs separately — they
  flow through the assistant's `usage` field which is the only
  thing we actually have access to.
- Trivial to test (`/N` is verifiable; byte counting needs
  fixtures for every encoding).
- We document the limitation: a single Read returning 100KB and
  a Bash returning 5 bytes get equal credit. Caveats in UI.

Input tokens go to the *first* tool unchanged (they were the
prompt that triggered the turn — already attributable).
Output tokens split per (α). Cache hits route through the same
denominator.

## Risks

**R1 — Numbers visibly change for existing users.** A user who
saw "Bash $4.20" in v0.2 may see "Bash $1.40, Read $1.40, Edit
$1.40" in v0.3. CHANGELOG must call this out loudly. Audit
mode (T09) lets them prove no data is lost.

**R2 — Reindex stalls cold-start.** 30k events rebuild in
estimated 5–8s on M2; older Macs ≥30s. Mitigation: show progress,
let the user defer if popover opens during rebuild.

**R3 — `tool_use` blocks counted wrong.** Some tool outputs
contain nested `tool_use` JSON (e.g. Plan tool listing other
tools); we count only the top-level blocks. Documented in
ADR-0015.

## Out of scope

- Changing the legal definition of "tool" (still string `name`
  field from JSONL, no normalization).
- Per-tool *subtotals by repo* — additive, but T07 already gets
  most of the value. Defer.
- Dashboard / report view (multi-day per-tool trend) — out of
  popover scope; would need a real window.
