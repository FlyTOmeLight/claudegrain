Status: themes locked 2026-05-10
Picks: **C (tool-level breakdown) + D (time-of-day heatmap + cycle-aware forecast)**

Detail plans:

- `docs/plans/v0.3-time-of-day.md` (theme D)

A (real distribution + Sparkle) and B (interactive widgets) and

v0.2 (rc5–rc10) shipped: control surfaces (budgets / quiet hours /
pause / commitments), forecast, desktop widget (3 sizes), polish
(keyboard / a11y / cold-start vitals / OAuth banner). Source of
truth: `docs/plans/v0.2-phase{3,4,5}-*.md`.

v0.3 picks 3 themes from the candidate list below. Each theme is
~1 week of focused work and ships an `.x` increment (0.2 → 0.3).
Out-of-scope items go to v0.4 / explicit deferral.

## Candidate themes

### A. Real distribution (Developer ID + notarization + Sparkle)
**Why:** v0.2 ships ad-hoc DMGs; users do `xattr -dr com.apple.quarantine`
on every install. App Group entitlement also doesn't validate at
runtime under ad-hoc → widget can't read host snapshots without
manual Xcode signing. Real distribution unblocks the widget for
non-developer users.

Tasks (rough):
- D-T01: Apply for Apple Developer Program / acquire Developer ID
  Application cert (user action; document in `docs/RELEASE.md`).
- D-T02: Wire `DEVELOPER_ID` + `DEVELOPMENT_TEAM` + `NOTARY_PROFILE`
  into release.yml as GH secrets.
- D-T03: Add Sparkle.framework dependency + `appcast.xml`
  generation step in build-dmg.sh. ADR for in-app updater (ADR-0013).
- D-T04: First-launch entitlement smoke test
  (`scripts/verify-entitlements.sh`) — runs in CI, fails fast on
  missing App Group.
- D-T05: GH Releases publish appcast.xml; Sparkle reads it.

Risks: Apple Developer Program is $99/yr — user gating. Sparkle
adds binary size + new attack surface. Notary throughput is
opaque (CI run could 10× longer).

Estimate: 8-12h.

### B. Interactive widgets (App Intents)
**Why:** macOS 14+ supports buttons in widgets via App Intents.
Currently widget is read-only; clicking it opens the host.
Could let users pause ingest, mark commitments paused, refresh,
without leaving the widget.

Tasks (rough):
- I-T01: ADR-0014 — App Intent / widget interaction surface.
  Decide which actions get widget-level buttons.
- I-T02: `PauseIntent` + `ResumeIntent` (`AppIntent` protocol).
  Communicate via App Group file flag the host polls.
- I-T03: `RefreshIntent` triggering `WidgetCenter` reload chain.
- I-T04: Wire buttons into Large layout (small/medium too small).
- I-T05: Snapshot update path — if user pauses via widget, host
  must observe within 30s to keep menu bar in sync.

Risks: App Intents on macOS are less mature than iOS. Cross-process
intent → host communication is tricky without sandboxing the host.

Estimate: 6-8h.

### C. Tool-level breakdown (replaces primaryTool attribution)
**Why:** ADR-0003 explicitly simplified to "100% of turn → first
tool_use block" with the caveat "UI must label this 'by primary
tool' — not precise per-tool billing". Power users have asked for
real per-tool split since v0.1. v0.3 replaces this with a
documented split algorithm.

Tasks (rough):
- T-T01: ADR-0015 — token attribution v2 (per-tool weighting).
  Two candidate algorithms: (a) split tokens proportionally by
  tool_use block count; (b) heuristic by tool_input/output byte
  size. Pick + justify.
- T-T02: `Cost/CostCalculator` accepts a strategy enum. Default
  switches to v2; `--legacy-attribution` flag preserves v1 for
  audit comparison.
- T-T03: Re-aggregate `EventsDatabase` with new strategy on next
  launch (schema migration handles backfill from JSONL).
- T-T04: Per-tool breakdown in popover (new section under spend).
  Replaces / augments `ModelMixRow`.
- T-T05: Migration checkpoint — old DB rows stay until rebuild
  from JSONL completes.

Risks: rebuild from JSONL on first v0.3 launch could take seconds
on heavy users — show progress UI. Existing users may be confused
by changed numbers. Need a "what changed" doc.

Estimate: 10-14h.

### D. Time-of-day analytics
**Why:** Currently burn-rate forecast is "this rate continues" —
ignores user's typical pattern. Knowing "you usually slow down
after 6pm" would make forecasts smarter.

Tasks (rough):
- TOD-T01: ADR-0016 — hourly bucket aggregation in `EventsDatabase`.
- TOD-T02: 24-hour heatmap view (popover, replaces or supplements
  the 7-day chart in scroll mode).
- TOD-T03: Forecast-aware-of-pattern: blend current burn with
  historical hourly average for the remaining hours of the
  session block.

Risks: heatmap UI is new design surface. Forecast-with-pattern is
a non-trivial probabilistic upgrade.

Estimate: 6-10h.

### E. Theme picker
**Why:** Phosphor / Thermal are bespoke but hard-coded by
`colorScheme`. Users have asked for "Solar", "Dracula", "GitHub".

Tasks: add a `Settings → Appearance` tab with 4-6 themes,
re-architect `Theme.swift` from a colorScheme switch into a
selectable enum + persisted preference. ~3-5h.

Risks: minor; mostly visual.

### F. Onboarding flow
**Why:** First launch is silent — user sees zero data, doesn't
know about the JSONL path, doesn't know to log in via `claude
/login` for OAuth. ADR-0001's three-tier model deserves user
explanation.

Tasks: a one-time wizard explaining JSONL ingestion, OAuth
optional benefits, where data is stored (Application Support).
~3-4h.

Risks: deciding what's worth onboarding without overwhelming.

## Picked: C + D

C unblocks the most-requested data quality fix (per-tool numbers)
and D delivers the most-requested forecast quality fix (cycle-aware
prediction). Together they upgrade the *analytics* spine of
Claudegrain.

A / B / E / F slip to v0.4. A in particular gates the public widget
release — until then ad-hoc users keep doing the Xcode self-sign
dance.

## Out of scope for v0.3 (defer)

- iOS / iPadOS port — separate milestone. Architecture changes
  (UIKit + WidgetKit different lifecycle) are non-trivial.
- Sandboxing the host app — would require cache.db migration to
  App Group container; touches every store path. Separate ADR.
- Multi-window / dockable popover — UX shift.
- Localization beyond EN+ZH (JP/KR/ES).
- Settings sync via iCloud — Apple's API churn here is too high.
- Tag/badge system on repos — useful but speculative.

## Sequencing

1. C first. Tool-attribution change touches Cost/CostCalculator +
   Store/EventsDatabase + popover; it's the load-bearing piece.
   Lands a new ADR-0015.
2. D second. Time-of-day analytics depends on the new aggregation
   shape that C will already have touched — single-pass migration.
3. Final rc cuts a milestone tag (likely v0.3.0 — drops the
   pre-1.0 rc cadence if confidence holds).

## Cross-cutting concerns

- **DB migration**: ADR-0002 says JSONL is source of truth, SQLite
  is materialized view. Both C and D may bump the cache schema —
  that's free per ADR-0002, just rebuild from JSONL on launch.
  Need a "rebuilding cache…" UI for users with large JSONL stores.
- **ADRs**: 0015 (tool attribution v2), 0016 (hourly bucket
  aggregation). Drafted alongside the plan files.
