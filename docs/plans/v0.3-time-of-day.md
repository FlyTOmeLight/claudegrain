# v0.3 — Time-of-day analytics + cycle-aware forecast (theme D)

Status: planning
Touches: ADR-0001, ADR-0002 (cache schema), Forecaster.

## Goal

1. **24-hour heatmap** in the popover (replaces / supplements the
   7-day spend chart in scroll mode). User can see at-a-glance
   when in the day they spend most.
2. **Cycle-aware forecast**: instead of "current burn × time
   remaining", blend *current* burn with the *historical hourly
   average* for the remaining hours of the session block /
   weekly window. The user's typical 9pm slowdown stops fooling
   the forecaster.

## Why

Current forecaster (`LimitEstimator`) assumes uniform burn rate
forward. If the user typically spends $0.10/min in the morning
but $0.05/min after 6pm, a 5pm forecast over-predicts the 5h
session block exhaustion. v0.2 has shipped the proactive
notifications path (ADR-0010 commitments) on top of this; better
forecasts mean fewer false alarms and better commitments.

The heatmap also surfaces the *pattern* the new forecast uses,
giving users a way to interrogate why the prediction looks the
way it does.

## Plan

### V3-T11 — ADR-0016 — hourly bucket aggregation
File: `docs/adr/0016-hourly-aggregation.md`. Two storage options:

(α) Add a `cost_per_hour(weekday, hour)` rolling-7-day summary
    table. Updated on every ingest tick.
(β) Compute on-demand via existing `costPerBucket(start, span,
    bucketSize)`. Slower but no schema bump.

Decision: (α). Pre-aggregated table is ~7×24 = 168 rows; trivial
to update incrementally; popover can query it in <1ms vs. the
multi-second on-demand path.

### V3-T12 — `EventsDatabase` schema bump (`hourly_buckets` table)
File: `Sources/ClaudegrainCore/Store/EventsDatabase.swift`.
Schema: `(weekday INT, hour INT, cost_usd REAL, tokens INT,
last_event_at REAL, sample_count INT, PRIMARY KEY(weekday, hour))`.
Updated by `IngestActor` on each successful event commit. 7-day
EWMA decay so the table tracks recent patterns, not all-time.
Acceptance: 4 new tests for incremental update, EWMA decay,
weekday rollover, sample-count floor (don't trust hours with <10
events).

### V3-T13 — `Forecaster.forecastSessionBlock` v2
File: `Sources/ClaudegrainCore/Forecast/Forecaster.swift`.
Take the existing forecast (current burn × remaining time) and
blend with hourly-pattern projection:
```
predicted_remaining_cost
  = α × (current_burn × time_remaining)
  + (1-α) × Σ hourly_avg(h) for h in remaining_hours
```
where α is a freshness weight: high (0.8) when the recent burn
sample is large; low (0.3) when it's a single 5-min bucket.
Acceptance: 5 new forecaster tests covering pure-pattern mode
(α=0), pure-current mode (α=1), blend at typical α=0.6, weekend
vs. weekday separation, insufficient-data fallback.

## Risks

**R1 — Heatmap is dense and may be wrong default**. Some users
won't care. We hide it behind expand/collapse in scroll mode and
opt-in in fixed mode. Default visibility: collapsed.

**R2 — Pattern-aware forecast cuts both ways**. A user who
deliberately changes habits (new project, new schedule) will see
the forecast lag the change. Document the EWMA half-life
(7 days) and let the forecaster down-weight when sample sizes
are thin (existing approach).

**R3 — Hourly aggregation costs CPU**. Each event hits one
indexed update — should be cheap. T19 is the smoke test.

## Out of scope

- Longer cycles (weekly / monthly). Separate aggregation, not
  worth in v0.3.
- ML model for forecast. EWMA-blend is the right complexity
  trade-off for now.
- Per-repo heatmap. Already crowded; stay aggregated.
- Time-of-day notifications ("you usually slow down by 6pm —
  pause?"). Speculative; would need ADR-0010 changes.
